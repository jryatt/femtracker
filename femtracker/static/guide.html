FEM Tracker user guide

FEM Tracker keeps your finite element studies in one place. It sends each job to your HPC over PuTTY, watches it run, and brings the results back into a database that remembers exactly how every result was made, so you stop juggling batch files, folders and spreadsheets.

Part 1Get started

What FEM Tracker does

It replaces the "copy files, run plink, wait, copy results back, paste numbers into a spreadsheet" routine with a queue you manage from a web page.

You describe a study once: which input files to upload, which commands to run on the HPC and which result files to bring back. You then queue jobs that differ only in their parameters, such as load or thickness. FEM Tracker does the rest in two separate steps:

Step 1: run

Creates a folder for the job on the HPC, uploads your inputs with pscp, and starts your commands in a detached tmux session with plink. The job keeps running if your PC sleeps or the network drops. FEM Tracker checks on it every minute.

Step 2: populate

When a run finishes, the result files come back to your PC and go into the database. Numbers such as Max_Mises = 212.4 become metrics you can compare across jobs. Optionally, the remote folder is then deleted.

The two steps are independent. A finished run whose results you haven't collected yet is simply "awaiting population". You can populate a job again at any time without re-running the analysis.

Every run is kept as a separate attempt, with the parameters, scripts, input files and git commit it used. Running a job again never overwrites earlier results. See Versions and history.

Everything stays on your PC. FEM Tracker talks only to your own HPC account, through the same PuTTY tools you already use.

Keys with a passphrase

FEM Tracker can't type a passphrase for you. Either leave it empty and protect the file with Windows permissions, or start Pageant (PuTTY's key agent) and add your key before starting FEM Tracker. plink uses keys held by Pageant automatically.

Accept the host key once

The first time you connect with PuTTY, it asks whether you trust the server's key. Answer Accept. Until you do, every FEM Tracker connection fails with "Cannot confirm a host key in batch mode".

Part 2Your first study

This walkthrough runs a small Abaqus load sweep on an L-bracket: the same model at several loads and thicknesses. You'll find the lightest bracket that stays below 240 MPa. Swap in your own model as you go; only the file names change.

Prepare the input folder

Put everything a job needs in one folder on your PC, for example C:\FEM\Bracket.

C:\FEM\Bracket\ ├── bracket_template.inp the model, with @placeholders@ for what changes ├── Pre_Processing.py fills in the placeholders for one job └── Post_Processing.py reads the .odb and writes Post_Results.txt

The model template

Write @name@ wherever a value changes between jobs. The names must match the parameters you'll give each job.

bracket_template.inp (excerpt)
*Shell Section, elset=BRACKET, material=AL6061
@thickness_mm@, 5
...
*Step, name=Load, nlgeom=YES
*Static
*Cload
TIP, 2, -@load_N@
*End Step

Pre-processing: one input file per job

FEM Tracker uploads the job's parameters as job_params.json next to your scripts. This script reads them and writes <job name>.inp.

Pre_Processing.py
# Runs on the HPC as:  abaqus python Pre_Processing.py <job_name>
import json
import sys

job_name = sys.argv[1]
params = json.load(open("job_params.json"))

text = open("bracket_template.inp").read()
for key, value in params.items():
    text = text.replace("@%s@" % key, str(value))

if "@" in text:
    sys.exit("A placeholder in the template has no matching job parameter")

with open(job_name + ".inp", "w") as f:
    f.write(text)
print("wrote %s.inp" % job_name)
Building the model in Abaqus/CAE instead?

Use a CAE script and the command abaqus cae noGUI=Build_Model.py -- {job_name}. Everything after -- reaches your script in sys.argv, and job_params.json works the same way.

Post-processing: numbers FEM Tracker can read

Write one Name = number per line. FEM Tracker turns each line into a metric you can compare across jobs.

Post_Processing.py
# Runs on the HPC as:  abaqus python Post_Processing.py <job_name>
import sys
from odbAccess import openOdb

job_name = sys.argv[1]
odb = openOdb(job_name + ".odb", readOnly=True)
frame = list(odb.steps.values())[-1].frames[-1]          # last frame of the last step

max_mises = max(v.mises for v in frame.fieldOutputs["S"].values)
max_disp = max(v.magnitude for v in frame.fieldOutputs["U"].values)
base = odb.rootAssembly.nodeSets["BASE"]                 # use your own node set name
reaction = sum(v.data[1] for v in frame.fieldOutputs["RF"].getSubset(region=base).values)
odb.close()

with open("Post_Results.txt", "w") as f:
    f.write("Max_Mises = %.2f\n" % max_mises)
    f.write("U_max = %.4f\n" % max_disp)
    f.write("Reaction_Force = %.1f\n" % abs(reaction))

If the .odb is missing or a field isn't there, the script stops with an error. The run is then marked failed, which is what you want. See Getting metrics out for other formats.

Why the grep line?

An Abaqus queue submission can return success even when the analysis aborted. Checking the .sta file for "THE ANALYSIS HAS COMPLETED SUCCESSFULLY" turns a silent failure into a failed run, before post-processing tries to read a broken .odb.

Queue names are site-specific

normal:wait:ppn16 is an example. Use the queue your site documents, and keep the part that makes the command wait. For Slurm, PBS and LSF equivalents, see Schedulers and waiting.

Queue jobs

On the study page, click Queue a job. Give it a name and the parameters that make it different.

  • Name becomes {job_name} in commands. Spaces and symbols turn into underscores, so "t6 F3000" becomes t6_F3000, a valid Abaqus job name.
  • Parameters are written as {"name": value, ...}, with quotes around names and around text values. Each one is available as {name} in commands and as @name@ in your template, through the pre-processing script.
  • Priority: higher numbers start first. Jobs with the same priority start in the order they were queued.
  • Override the study run setup lets one job use different commands or files, for example a longer queue for a fine mesh. Leave it closed for normal jobs.

For the sweep, queue t4 F1000, t4 F1500, t4 F2000, t4 F2500 and t5 F2500, changing load_N and thickness_mm each time.

Watch them run

Within a minute the first jobs turn from queued to running. Up to four run at once; the rest wait their turn.

The Queues page shows every study's waiting and running jobs. You can change priorities or cancel jobs there.

Watching a job live on the HPC

Log in with PuTTY as usual, then either attach to the job's session or follow its log:

tmux attach -t fem_1_1_t4_F1000        # the session name is shown on the job and on the Queues page
tail -f /scratch/jsmith/fem_tracker/study_1/job_1/attempt_1/run.log
Leave a tmux session with Ctrl+B, then D

That detaches and leaves the job running. Pressing Ctrl+C inside the session stops your analysis.

Look at the results

Click a job to open its panel. It has a tab for each attempt, showing both steps, what went into the run and everything that came back.

  • Run summary holds the metrics read from Post_Results.txt, plus the last lines of run.log.
  • Each file you asked for is listed. Small ones have a Download link. Large ones show where they are: on this PC, or still on the HPC. See Where result files go.
  • Show HPC script in step 1 shows exactly what ran, with your placeholders filled in. It's the first thing to look at when a command didn't do what you expected.
  • Provenance lists the input files the attempt used, with checksums, and the git commit of your input folder.

Compare, then write it down

The Compare metrics table at the bottom of the study page lines up every metric from every job. When you've drawn a conclusion, click Edit study and write it in Study results. It appears at the top of the study, next to the description.

Fix a failed run

A failed job turns red and tells you why. The end of run.log is usually enough to see what went wrong.

  1. Read the messageEvery command is echoed into run.log with a + in front, so you can see which one failed, followed by its output.
  2. Fix the causeEdit the template or scripts in your local folder, change the study's commands, or adjust the job. Changes to the run setup apply to jobs the next time they start.
  3. Click Run again…Say what you changed, adjust the parameters if needed, and click Queue attempt. The failed attempt stays in its own tab, with its error and its own folder on the HPC, so you can compare.

If the population step failed instead, the analysis itself is fine. Fix the cause, often a result file name, then click Populate again. Nothing is re-run.

Part 3Everyday use

Manage jobs

Every action is on the job's panel; the most common ones are also on the Queues page.

Cancelling scheduler jobs

Ending the tmux session stops the command that was waiting. Whether the solver job on the cluster stops too depends on your scheduler. Add a cancel command so it always does: see the table in Schedulers and waiting.

Once a job's first attempt has started, its parameters are frozen; use Run again… to try other values. To run one job with a different command, use Override the study run setup when you queue it.

Add results by hand

Hand calculations, test data or a screenshot from Abaqus/Viewer can sit next to the automatic results.

At the bottom of a job's panel, use Add a result by hand. Give it a name, a description, optional metrics as JSON (for example {"Max_Mises": 209}), and optionally a file. Results added by hand belong to the job rather than to an attempt. They appear in the study's comparison table marked "by hand", and are the only results you can delete.

If the file is a .ipynb, a View notebook button appears next to it: markdown cells, code (shown, not run) and its stream/image/table/error outputs, read-only — no kernel runs inside FEM Tracker.

Import runs done elsewhere

Already ran something with your old batch file? Load it into a study so it sits alongside everything else, marked as imported.

With FEM Tracker running, open a command prompt in the FEM Tracker program folder and run:

FEMTracker.exe import --study 1 --name "t4 F2500 (2024 run)" --params "{\"load_N\": 2500, \"thickness_mm\": 4}" --note "Run with the old batch script" "C:\FEM\old_runs\run_3"

This creates a job with one imported attempt. Every file in the folder is stored, and recorded with its checksum. Metrics are read exactly as for normal runs. The study number is the # in the address bar or the sidebar order; --params is optional.

To add a folder as a new attempt of an existing job instead, use FEMTracker.exe populate --job 12 --local-dir "C:\FEM\old_runs\run_3" --note "…".

The program folder is %LOCALAPPDATA%\Programs\FEM Tracker for a per-user install, or wherever you unzipped the portable version.

Notebook

A place to write findings and decisions next to the runs they're about, with screen grabs, links to jobs and attempts, and a full history. Open it from the Notebook tab next to Jobs on a study's page.

An entry has a title, a kind (note, finding or decision), optional tags, and a body written in Markdown (the default) or raw HTML. The editor sits next to a live preview that updates about a third of a second after you stop typing. Ctrl+S saves; closing or navigating away with unsaved changes asks first.

Screen grabs

Paste a screenshot straight into the body (Win+Shift+S on Windows, Cmd+Ctrl+Shift+4 on a Mac, then paste), drag an image file in, or use the Image… button in the toolbar. PNG, JPEG, GIF and WebP are accepted (not SVG); each one is checked by its actual contents, not just its name, and refused if it's over the [notebook] max_image_mb setting (default 20 MB). The same image pasted twice is stored once: it's identified by its checksum, the same way input files are.

Pasting inserts ![caption](asset:<checksum>) at the cursor, with the caption selected so you can type over it immediately — there's no dialog to stop and fill in. The caption is the image's alt text.

To reuse an image rather than attaching a new copy, use Existing image…. It lists two things: screen grabs already pasted into this study's notebook (in any entry), and results in this study that are images (a plot a job produced, say). Picking one inserts ![caption](asset:<checksum>) or ![caption](result:<id>) as appropriate; neither stores a second copy.

Images show at their own width, capped at the column width; click one to open it at full size.

Linking to runs

Use the [[ ]] Link… button, or type the reference directly, to point at something tracked elsewhere in the database. Each renders as a link that opens the job panel at the right attempt:

WriteLinks to
[[job:5]]job 5
[[attempt:5/2]]job 5, attempt 2
[[result:123]]result 123
[[metrics:job:5]]embeds a small table of job 5's current metrics, kept live each time the entry is viewed
[[git:a1b2c3d]]the attempt(s) whose recorded git commit starts with that prefix — paste any length you'd use with git log --oneline

A reference to something that's since been deleted renders as a plain "not found" marker rather than breaking the entry. Every job an entry mentions (directly, through an attempt, or through a git commit) is recorded as a link, re-checked on every save; the job's own panel lists "Notebook entries about this job" so you can find your way back from either direction.

Attaching a folder

Besides single images, an entry can carry a whole folder as one attachment — useful for a folder of input files you want to keep next to a note, without them being part of a job's own tracked inputs. Use Attach folder… and pick a folder; FEM Tracker zips it (keeping the folder structure) and uploads it as one object, content-addressed the same way images are, so attaching the same folder twice stores it once. This inserts [[attachment:<checksum>]], which renders as a download link with the file name and size. Zips over the [notebook] max_attachment_mb setting (default 200 MB) are refused with a clear message.

Findings

Set an entry's kind to Finding and it appears, with its date, in a short list under Study results on the study's page — the place to look for what a study concluded without reading every entry.

History

Like studies and attempts, nothing in the notebook is overwritten: every save keeps a full copy of the title, kind, tags, format and body. Open History on an entry and pick any two saved versions to see them rendered side by side.

Archive on an entry's toolbar is this notebook's version of delete: the entry is hidden from the list, but nothing is removed. Tick Show archived in the notebook's filters to see it again and Restore it.

In exports

A study export (see Export to git) includes a notebook/ folder: one Markdown or HTML file per entry with front matter for its title, kind, tags, dates and linked jobs, a notebook/assets/ folder of the images it uses, a notebook/attachments/ folder of the zipped folders it uses, and notebook/history.json with every revision. Image and [[ ]] links are rewritten to relative paths and plain links so the files read correctly on GitHub or GitLab on their own, without FEM Tracker running.

Rendering is sanitized on the server

The preview, the saved view and the export all go through the same Markdown renderer and HTML sanitizer, so a page shared over the network can't be used to run a script in a colleague's browser. Raw HTML entries get the same treatment: scripts, iframes, forms, event-handler attributes and javascript: links are stripped; only images served from FEM Tracker itself are allowed.

Study classes and KPIs

A study class is a reusable template: a named kind of study (say "Static Strength" or "Fatigue") with a standard list of KPIs it's expected to report. Assign the same class to every study of that kind, and their results compare consistently instead of each study inventing its own metric names.

Manage classes from Study classes in the sidebar. A class has a name, a description, and a list of KPIs; each KPI is a name (for example "Max Stress"), the exact metrics field it expects a job to report (for example Max_Mises, matching what you'd see in the study's Compare metrics table), and an optional unit.

Using a class in a study

Pick a class from the Study class field when creating or editing a study. The study page then shows a KPIs box: one row per KPI, with a dropdown to say which job in this study supplies it. That's the "pointer" — a KPI doesn't hold a value itself, it points at a job, and its value is always that job's current result for the expected metrics field, re-read live.

Shown valueMeans
a number, with its unitthe pinned job's latest populated attempt (or a hand-added result) currently reports that metrics field
not reporteda job is pinned, but nothing it has reported uses that exact metrics field name — check the spelling in your post-processing script, or in Post_Results.txt
not pinnedno job has been chosen for this KPI yet

Because the match is exact, a KPI that stays "not reported" is a visible prompt to name your metric the same way the class expects — that's the mechanism, not a formula or any averaging. Changing a study's class clears its existing pins, since they belonged to the old class's KPIs; moving back to "No class" clears them too. A study export includes kpis.json with the class name and each KPI's resolved value at export time.

One class can extend another

A class can have a parent class, the same idea as a base class in code: it inherits every KPI the parent defines, on top of its own. Give "Section of the Plane" a Mass KPI, then make "Crash Model" a child of it with its own Peak G KPI, and a study classed as "Crash Model" expects both — Mass inherited, Peak G its own. Chains of any length work the same way: a class inherits from its parent, which inherits from its parent, and so on.

If a class defines a KPI with the same metric key as one it would otherwise inherit, its own definition wins — the same as overriding a method shadows the inherited one. The class editor's Effective KPIs table always shows the full picture: every KPI the class actually uses, each marked "this class" or "inherited from …". Only single inheritance is supported (one parent, not several); FEM Tracker refuses to set a parent that would create a cycle, including making a class its own ancestor.

Part 4Adapt it to your cluster

Schedulers and waiting

FEM Tracker treats a job as finished when its last command ends. So the command that solves must wait for the analysis.

If a submit command returns straight away, for example plain sbatch, the job is marked finished within seconds and population finds no results. Every scheduler has a waiting mode:

SchedulerWaiting submitCancel command to add
Abaqus site queuesabaqus j={job_name} ... -queue normal:waitabaqus terminate job={job_name}
Slurmsbatch --wait -J {job_name} solve.sh {job_name}scancel --name={job_name}
PBS Proqsub -W block=true -N {job_name} -v JOB={job_name} solve.pbsqdel $(qselect -N {job_name})
LSFbsub -K -J {job_name} -n {cpus} bash solve.sh {job_name}bkill -J {job_name}
Grid Engineqsub -sync y -N {job_name} solve.sh {job_name}qdel {job_name}

These waiting modes also pass on the job's exit code, so a failed analysis becomes a failed run.

Example: Abaqus through Slurm

Keep a small batch script in your local input folder, and make sure the upload list includes it (*.sh):

solve.sh
#!/bin/bash
#SBATCH --ntasks=16
#SBATCH --time=04:00:00
#SBATCH --output=slurm.log
module load abaqus/2024
abaqus job=$1 cpus=$SLURM_NTASKS double=both interactive

Commands in the run setup:

abaqus python Pre_Processing.py {job_name}
sbatch --wait -J {job_name} solve.sh {job_name}
grep -q "COMPLETED SUCCESSFULLY" {job_name}.sta
abaqus python Post_Processing.py {job_name}

Add slurm.log to the files to bring back if you want the scheduler's output too.

Modules and environment

Commands run in a bash login shell, so whatever your .bash_profile sets up is available. If the solver needs a module, make it the first command, for example module load abaqus/2024.

Where the waiting happens

The waiting command runs on a login node, inside tmux, as your PuTTY batch scripts did. It uses almost no resources. A few sites stop long-running processes on login nodes. If jobs fail with "No heartbeat" after a fixed time, ask your HPC team, or move the whole command chain into a batch job.

Parameters and placeholders

Anything in curly braces is filled in per job before the commands reach the HPC.

{attempt}the attempt number, for example to keep attempts apart in a shared results folder
{any_parameter}that parameter's value, if it is a number, text, or true/false
  • Placeholders work in commands, files to upload, files to bring back and cancel commands. For example, bring back only this job's database with {job_name}.odb.
  • Shell variables such as $HOME or ${SLURM_NTASKS} are left alone.
  • A placeholder with no matching parameter is sent unchanged. If {cpu} shows up in run.log, check for a typo against cpus.
  • All parameters, including lists and nested values, are also written to job_params.json in the job's folder for your scripts to read.

Other solvers

Nothing in FEM Tracker is Abaqus-specific. The run setup is just files and shell commands.

CalculiX

python3 Pre_Processing.py {job_name}
ccx -i {job_name}
python3 Post_Processing.py {job_name}

Bring back {job_name}.frd and Post_Results.txt. Wrap ccx in a waiting scheduler submit if it shouldn't run on the login node.

Ansys Mechanical APDL

sbatch --wait -J {job_name} solve_ansys.sh {job_name} {cpus}

Inside solve_ansys.sh, call your site's MAPDL executable in batch mode, for example ansys<version> -b -np $2 -i $1.dat -o $1.out. Have your APDL macro write a Post_Results.txt with *CFOPEN and *VWRITE.

Getting metrics out

Metrics are the numbers compared across jobs. There are three ways to provide them, from simplest to most control.

1. Name = number lines (default)

FEM Tracker reads every retrieved text file (.txt, .csv, .dat, .out, .log, under 5 MB, except run.log). It keeps each line that is a name followed by a single number:

LineRead as
Max_Mises = 212.4Max_Mises: 212.4
U_max: 0.83U_max: 0.83
Reaction_Force,1520Reaction_Force: 1520
Freq_1 1.432e2Freq_1: 143.2
Max stress (MPa) = 212Max stress (MPa): 212
Mass = 1.2 kgignored: text after the number. Put units in the name instead: Mass_kg = 1.2.
Solver printouts can add noise

Bringing back a solver's own .dat or .out file may add stray metrics, because some of its lines look like "name number". Use one of the two options below to control exactly what's stored.

2. metrics.json

Have post-processing write a metrics.json, and add it to the files to bring back. When present, it's used instead of reading text files.

import json
json.dump({"Max_Mises": max_mises, "U_max": max_disp, "Mass_kg": mass},
          open("metrics.json", "w"))

3. manifest.json: full control

A manifest.json in the files to bring back decides exactly which results are created: their names, descriptions, metrics and attached files. Every file it names must also be in the list of files to bring back.

{"results": [
  {"name": "Static, load case A", "description": "Peak at the fillet radius",
   "metrics": {"Max_Mises": 212.4, "U_max": 0.83}, "file": "Post_Results.txt"},
  {"name": "Modal", "metrics": {"f1_Hz": 143.2, "f2_Hz": 388.0}},
  {"name": "Deformed shape", "file": "deformed.png"}
]}

Where result files go

Small files live in the database. Large ones, typically .odb and .rst, are kept as files, and FEM Tracker records where.

Downloads go to Documents\FEM Tracker results\study_<s>\job_<j>\attempt_<n>\population_<k>\. Every attempt and every population round has its own folder, so nothing downloaded earlier is replaced.

That results folder is FEM Tracker's record

The database points at files in it. Copy files elsewhere before editing them, rather than editing them in place.

Scratch space is often purged

Many HPCs delete old files from scratch automatically. Large files "on the HPC" disappear with them. If you need them long-term, set large_files = download, or bring back only what you need, for example a reduced .odb.

Part 5How it works

Versions and history

Nothing FEM Tracker records is overwritten. Each run of a job is an attempt, with a frozen record of exactly how it was made.

When an attempt is handed to the HPC, FEM Tracker freezes a copy of everything that went into it. Changing the study's commands later, editing your scripts, or running the job again never alters an earlier attempt or its results.

Each attempt keepsSo you can

every input file's name, size and SHA-256 checksum, plus a copy of each file up to store_inputs_max_mbdownload the precise model and scripts behind a result
the git commit of your input folder, and whether it had uncommitted changesfind the version of your model in your own repository

A job's parameters can be edited until its first attempt starts. After that they're frozen, and changes go into a new attempt.

Run a job again

Open the job and click Run again…. Say why, and adjust the parameters if needed. The new attempt uses the study's current run setup and your input folder's current files, and records both.

Run again… is greyed out while an attempt is still queued or running; cancel that first if you've changed your mind.

Compare attempts

A job with more than one attempt has a tab for each, newest first, and a Compare attempts button:

The study's Compare metrics table always uses each job's latest populated attempt, and says which one. A newer attempt that failed doesn't hide the last good result.

Provenance: what went into a result

Keep your input folder in git

If C:\FEM\Bracket is a git repository (or inside one), every attempt records the commit. Commit before you queue jobs: an attempt made "with uncommitted changes" still has its files stored, but they don't match any commit. Git for Windows is enough; FEM Tracker just runs git if it's installed.

Reproduce an old attempt exactly

  1. Get its inputsEither check out the recorded commit in your input folder (git checkout 8a67014177), or download the stored input files from the attempt's provenance section into a fresh folder.
  2. Match the run setupCompare the study's current run setup with the attempt's (Show HPC script). If they differ, create a study with the old setup; the attempt's frozen copy tells you exactly what it was.
  3. Run it againClick Run again… with the attempt's parameters and a note such as "Reproducing attempt 2". Then compare the two attempts.

Population rounds

Populate again doesn't replace results. It adds a new round, which becomes the current one. Earlier rounds stay available under Show … results from earlier population rounds, and each round's files have their own folder on your PC. Use it after changing Files to bring back or your metric format.

Study history

Every saved version of the study's description, study results, run setup and name is kept. Click History on the study page:

What can still be deleted

Results you added by hand can be deleted one at a time. Automatic results can't: they're part of an attempt's record. Deleting a whole job or study removes all of its attempts and results from the database; files on your PC and on the HPC are left alone.

Export to git

Turn a study into plain files you can commit, review in pull requests and archive with your project.

Click Export on the study page to download a zip, or write straight into a folder from the command line:

  • Files over 20 MB are listed in results.json or attempt.json with their checksum and location instead of being copied. Change the limit with --max-file-mb, or keep big files in Git LFS.
  • metrics.csv opens directly in Excel for plots and reports.

What happens on the HPC

Each attempt gets its own folder, so jobs and attempts running side by side never touch each other's files.

/scratch/jsmith/fem_tracker/ remote_workdir └── study_1/ └── job_5/ ├── attempt_1/ each attempt runs in its own folder └── attempt_2/ ├── Pre_Processing.py … your uploaded inputs ├── job_params.json this attempt's parameters ├── fem_run.sh the generated script that runs your commands ├── run.log everything the commands printed, each command marked with + ├── .fem_started start time ├── .fem_heartbeat touched every 60 s while running ├── run_status.json exit code, written when the commands end ├── cancel.log output of your cancel commands, if cancelled └── design_load_F2500.inp, .odb, .sta, … whatever your solver writes

How FEM Tracker knows a job's state

It never relies on staying connected. Every poll_seconds, one plink call checks all your running jobs at once:

  • run_status.json exists: the job ended. Exit code 0 means finished; anything else means failed, with the end of run.log attached.
  • Heartbeat is recent: still running.
  • Heartbeat older than heartbeat_timeout_min and no status file: the job was killed (node reboot, process limits, a manual kill) and is marked failed.
  • No heartbeat start_timeout_min after starting: the script never ran. See run problems.

These are plain files on the shared filesystem, so the check gives the right answer whichever login node plink lands on. If your host name is a load-balanced alias, that matters: the batch builder's tmux has-session check can be fooled by it.

To see the exact script for a job, click Show HPC script on its panel.

Part 6Running it day to day

Keeping it running

FEM Tracker only moves jobs forward while it's open. The analyses themselves don't need it.

  • PC asleep, off, or FEM Tracker closed: running jobs carry on. Nothing new starts, and nothing gets populated. When FEM Tracker starts again, it catches up within one check.
  • Start at sign-in: tick the option in the installer. Or put a shortcut to FEMTracker.exe start --no-browser in shell:startup, set to run minimised.
  • Many jobs: each check is one SSH login. If your site limits logins, raise poll_seconds to 120 or 300.
  • Licence tokens: max_active_runs caps how many jobs this PC runs at once. Set it to what your Abaqus tokens or fair-share allow.

Sharing with colleagues

One FEM Tracker can serve a small team's browsers. The jobs still run on the HPC as the person whose PC runs it.

  1. Listen on the networkIn [server], set address = 0.0.0.0 and restart. Allow FEM Tracker when Windows Firewall asks, on private networks only.
  2. Share the addressColleagues open http://your-pc-name:8000 in their browser.
There is no login

Anyone who can reach the page can queue, cancel and delete jobs, and every job runs under your HPC account. Only share on a trusted office network, never on the internet or on guest Wi-Fi.

If each engineer should run jobs under their own account, each of them installs FEM Tracker on their own PC.

Backups, moving and upgrading

Back up

Everything is in one file: fem_tracker.db in the data folder (Start › FEM Tracker › FEM Tracker data folder). Close FEM Tracker, then copy that file. If files ending in -wal or -shm are next to it, copy them too. Keep your config.ini and results folder in the same backup.

Move to a new PC

  1. Install on the new PCand run it once, then close it.
  2. Copy the dataCopy fem_tracker.db into the new data folder, and config.ini to %APPDATA%\FEMTracker.
  3. Keep the agent nameRunning jobs belong to the PC that started them. In [agents], set name to the old PC's computer name, so the new PC keeps watching them. You'll find the name under "Populated … by" on any populated job, or in Settings › System › About on the old PC.

Upgrade

Run the newer installer; it replaces the program and keeps your data. If a new version can't read an old database, FEM Tracker says so when it starts. Move the old database file aside, start fresh, and keep the old file for reference.

Uninstall

Use Settings › Apps or the Start menu's Uninstall FEM Tracker. Your database, settings and downloaded results are kept; delete the data folder yourself if you no longer need them.

Troubleshooting

Find the message you see. The full log is femtracker.log in the data folder's logs subfolder.

Connection

Sidebar says "Run agent: not set up"The grey text lists what's missing.

A required setting is empty or points to a file that doesn't exist. Open the settings, fill in what's listed, save, and restart FEM Tracker. Test HPC connection lists the same problems.

"Cannot confirm a host key in batch mode"

PuTTY hasn't stored this server's key yet. Connect once with PuTTY to exactly the same host name, and accept the key. If the HPC team changed the server's key, PuTTY warns you; confirm the change with them first.

"Server refused our key" or "Access denied"

The key isn't authorised for this user. Check user, and that the public half of the key is in ~/.ssh/authorized_keys on the HPC. Log in with PuTTY using the same .ppk to confirm.

It works in PuTTY, but FEM Tracker hangs or asks for a passphrase

The key has a passphrase, which batch mode can't type. Load the key into Pageant before starting FEM Tracker (see Connect). If your HPC needs a one-time code at every login, batch access isn't possible; ask the HPC team about key-only access.

"Program not found: …plink.exe"

PuTTY is not installed in the usual place. Install it from putty.org, or set plink and pscp to the full paths of the two .exe files.

Sidebar says "can't reach the HPC"

The connection worked before and now fails: VPN off, network down, or HPC maintenance. Nothing is lost. FEM Tracker keeps retrying, and jobs already running continue. Hover over the message to see plink's error.

Runs

"Could not start the job: No input file matches '*.inp' in …"

A pattern in Files to upload found nothing in the local input folder. Check the folder path in the run setup and that the files are there. Patterns are relative to that folder, not to where FEM Tracker is installed.

A job finishes in seconds, and population then finds no results

The solve command handed the job to the scheduler and returned straight away. Use its waiting mode (Schedulers and waiting). run.log shows the submit message, and no solver output after it.

"A command exited with code N"

Look at the end of run.log on the job: the line starting with + is the command that failed. For Abaqus, bring back *.msg and *.dat to see solver errors in the results. Fix the problem, then click Run again….

"Started … but fem_run.sh never ran"

The job was launched but never started. Log in with PuTTY, then run the job's script by hand to see the error, for example bash -l /scratch/jsmith/fem_tracker/study_1/job_7/attempt_1/fem_run.sh. Common causes: a login script (.bash_profile) that fails or waits for input, a full disk quota, or a remote folder you can read but not write.

"No heartbeat for N min: the job was killed or the node went down"

The waiting process on the login node disappeared: the node rebooted, the site stopped long-running processes, or someone killed the tmux session. The analysis may still be running under the scheduler. Check with squeue or qstat, then click Run again…. If it keeps happening at a fixed time, ask your HPC team about login-node process limits.

A cancelled job is still running on the cluster

Add the scheduler's cancel command to Extra commands when cancelling (see the table in Schedulers and waiting). For now, cancel it by hand with scancel, qdel or abaqus terminate.

"This job has already run; its parameters are frozen"

Parameters can only change until a job's first attempt starts. Click Run again… and enter the new values; the earlier attempt keeps the old ones.

"Run again…" is greyed out, or "Attempt N is still queued or running"

A job runs one attempt at a time. Wait for it to finish, or cancel it, then run again.

An input file says "not stored"

It was larger than store_inputs_max_mb, so only its checksum was recorded. Raise the limit if you want copies of big meshes too; the database grows by each distinct file's size.

Provenance says "not a git repository"

Either the input folder isn't in a git repository, or git isn't installed on this PC (Git for Windows), or record_git = no. Everything else is still recorded.

Population

"Nothing in … matches: Post_Results.txt"

A file in Files to bring back wasn't created. Check that post-processing ran (it's in run.log) and that the name matches exactly, including upper and lower case. Linux is case-sensitive. Fix it, then click Populate again.

"Remote run folder is gone"

The attempt's folder was deleted, usually by a scratch clean-up policy or by hand. The results can't be collected any more. Click Run again… to make a new attempt.

Results are there, but there are no metrics

The retrieved text files don't have Name = number lines, or the numbers have units after them. Open the file from the job to check, or write a metrics.json (see Getting metrics out).

Strange extra metrics appear

A solver printout (.dat, .out) was read too. Stop bringing it back, or write metrics.json, which takes priority.

The app

"Could not start the web server on port 8000"

Another program uses that port. Set port = 8010 (or any free number) in [server], and open the new address.

"Settings problem: … expected a whole number"

A value in config.ini has the wrong form. The message names the section and setting. Numbers are plain digits; yes/no settings take yes or no.

"… was made by an older FEM Tracker"

The database comes from an incompatible version. Move fem_tracker.db out of the data folder and start again. Keep the old file as a record.

The page says "No HPC agents running"

FEM Tracker was started with server, or both agents are switched off in [agents]. Start it from the Start menu entry FEM Tracker.

Questions

Does my PC have to stay on while jobs run?

No. Analyses run on the HPC regardless. Your PC only needs to be on to start queued jobs and to bring results back.

Is any data sent anywhere?

No. Everything stays on your PC and your HPC account. The only network traffic is plink and pscp to your HPC, and your browser talking to FEM Tracker on your own PC.

If I change a study's run setup, what happens to existing jobs?

Attempts that have already started keep the setup they were frozen with, including for population. Queued attempts pick up the change when they start. To bring back an extra file from an old attempt, run the job again, or fetch the file by hand if the remote folder still exists.

Can I undo a "Populate again"?

There's nothing to undo: the earlier round is still there under Show … results from earlier population rounds, and its files are in their own folder.

Can two people use the same HPC account through FEM Tracker?

It's better if each person runs FEM Tracker with their own account, or shares one FEM Tracker's page (see Sharing). Don't run two copies with the same [agents] name.

Can I use it without PuTTY?

Yes. Set transport = openssh to use the ssh and scp built into Windows 10 and 11, with an OpenSSH key in ssh_key.

How big can the database get?

Many gigabytes is fine. Most space goes to stored files; lower max_blob_mb to keep more files outside the database.

Glossary

Study
A group of related jobs sharing one run setup, with a description and your conclusions.
Job
Something to compute: a name, parameters and a priority. Each time it runs, it gets a new attempt.
Attempt
One run of a job, with a frozen copy of its parameters, run setup, script and input files, and its own results. Earlier attempts are never changed.
Population round
One pass of bringing an attempt's results back. Populate again adds a round; earlier rounds are kept.
Provenance
The record of what went into a result: input file checksums (and copies), the git commit of the input folder, the parameters and the exact script.
Run setup
Which files to upload, which commands to run, and which files to bring back. Set on the study; a job can override parts of it.
Parameters
The values that make a job different, written as JSON. Available as {name} in commands and in job_params.json.
Run (step 1)
Uploading a job, running its commands on the HPC, and watching until they end.
Population (step 2)
Bringing a finished job's result files back and storing them in the database.
Agent
The part of FEM Tracker that does one step in the background: the run agent or the populate agent.
Heartbeat
A file the running job updates every minute, so FEM Tracker can tell a running job from a dead one.
Metric
A named number from a result, such as Max_Mises, compared across jobs on the study page.
Run folder
The attempt's own folder on the HPC: remote_workdir/study_<s>/job_<j>/attempt_<n>.
